Tor on Linux

I show you how to install and run Tor on Arch Linux.

Install

sudo pacman -S tor torsocks torbrowser-launcher

Initialize

sudo systemctl enable --now tor.service
systemctl status tor

The status should show active (running). The log should show Bootstrapped 100%.

Check that Tor is working

curl --socks5-hostname 127.0.0.1:9050 https://check.torproject.org/api/ip

Expected output:

{"IsTor":true,"IP":"185.220.101.169"}

"IsTor":true means the request left through a Tor exit node. The IP is the exit node's address, not yours.

Check for DNS leaks

A request can go through Tor and still leak DNS. If the client resolves the hostname locally, the lookup goes to your normal resolver, which can see which domain you visited.

Terminal A: capture DNS packets.

sudo tcpdump -i any -n port 53

Terminal B: run the following commands.

Case 1: --socks5 (DNS leak)

curl --socks5 127.0.0.1:9050 https://check.torproject.org/api/ip

Terminal A shows:

127.0.0.1.51689 > 127.0.0.1.53: AAAA? check.torproject.org.
127.0.0.1.53218 > 127.0.0.1.53: A? check.torproject.org.
127.0.0.1.53 > 127.0.0.1.53218: A 116.202.120.181

curl asked the local resolver (127.0.0.1:53) for the IP of check.torproject.org, then sent only the IP address to Tor. The lookup happened outside Tor, and the local resolver forwarded it upstream. This is a DNS leak.

Case 2: --socks5-hostname (no leak)

curl --socks5-hostname 127.0.0.1:9050 https://check.torproject.org/api/ip

In contrast, Terminal A shows no query for check.torproject.org. curl passes the hostname to Tor, and the exit node resolves it. The local resolver is never used in this case.

To avoid DNS leaks, the following commands are equivalent:

curl -x socks5h://127.0.0.1:9050 https://check.torproject.org/api/ip
torsocks curl https://check.torproject.org/api/ip
export ALL_PROXY=socks5h://127.0.0.1:9050

Change the exit node

Tor builds a circuit of three relays: entry (guard), middle, and exit. Websites only see the exit node's IP address. You can ask Tor to build a new circuit, which usually gives you a different exit node.

Method 1: Send NEWNYM through the control port

Use this method when you want to switch circuits for all new connections.

NEWNYM is a signal sent to Tor's control port. It tells Tor to use fresh circuits for new connections, so the exit node and IP usually change.

1. Generate a hashed password

tor --hash-password <password>

I use abc as the password here, which generates the following hash.

2. Add the following to /etc/tor/torrc

ControlPort 9051
HashedControlPassword 16:4CC473A06D893E72600A8B6574BDB9E278E048334D9007AD4469463A04

ControlPort listens on localhost only by default. Do not expose it to other machines.

3. Restart Tor

sudo systemctl restart tor

4. Send the NEWNYM signal

printf 'AUTHENTICATE "abc"\r\nSIGNAL NEWNYM\r\nQUIT\r\n' | nc 127.0.0.1 9051

Expected response (250 OK twice):

5. Check that the exit IP changed

curl --socks5-hostname 127.0.0.1:9050 https://check.torproject.org/api/ip

Method 2: Use a different SOCKS username

Use this method when you want different circuits for different commands, without touching the control port.

Tor isolates circuits by SOCKS username and password. Connections that use different credentials never share a circuit, so they usually leave through different exit nodes.

curl -x socks5h://a:x@127.0.0.1:9050 https://check.torproject.org/api/ip
curl -x socks5h://b:x@127.0.0.1:9050 https://check.torproject.org/api/ip

Here a and b are arbitrary usernames, and x is a dummy password.

As with Method 1, a different circuit does not guarantee a different exit IP.

Bridge

A Bridge is a Tor relay that is not listed in the public relay list. Generally, Tor connects to a publicly listed entry node. Because the list is public, an ISP or a government can block those IP addresses or detect that you are using Tor. Bridges are not in the public list, so they are much harder to block in bulk.

Bridges can be combined with a pluggable transport such as obfs4. obfs4 makes your traffic look like random data, so it is hard to recognize as Tor. Tor traffic is already encrypted, so the ISP cannot read its contents anyway. What obfs4 hides is the fact that you are using Tor at all.

How it works

Normal: you -> public entry node -> middle -> exit
Bridge: you -> bridge (via obfs4) -> middle -> exit

1. Install the plugin

lyrebird is the pluggable transport that implements obfs4. It is not in the official repositories, so install it from the AUR. The binary is installed as /usr/bin/lyrebird.

yay -S lyrebird-proxy

2. Get bridges from the official site

Get obfs4 bridges from https://bridges.torproject.org.

3. Add these bridges to /etc/tor/torrc

Write UseBridges 1 once, then add one Bridge line per bridge. Tor uses one bridge at a time. The others are backups, used when the current one is blocked or goes down.

UseBridges 1
ClientTransportPlugin obfs4 exec /usr/bin/lyrebird
Bridge obfs4 23.94.174.196:9130....
Bridge obfs4 100.8.170.63:50164....

4. Restart Tor

sudo systemctl restart tor
journalctl -u tor -f

The log should show Bootstrapped 100%.

5. Check that bridges are used

The outgoing connection to the bridge is made by lyrebird, not by tor, so filter by lyrebird. The remote address should match one of your bridge IPs. The connection between tor and lyrebird on 127.0.0.1 is local and is expected.

sudo ss -tnp | grep lyrebird
